# 代码结构说明

本目录用于存放开题后续实验代码。代码会按照行动方案分阶段推进，避免把二维检测、单模态三维检测、图像+雷达多模态三维检测和后续退化实验混在一起。

当前已完成第一阶段二维目标检测 Demo、第二阶段 PointPillars 单模态三维目标检测展示、第三阶段 MVX-Net 图像+雷达多模态三维目标检测展示，以及第四阶段复杂工况样例构造与初步检测对比。
第四阶段采用“多个原始样例，一一对应多种复杂工况”的组织方式，并已整理 clean/complex 检测结果对比。

## 各部分作用

### `README.md`

说明代码目录的整体用途、当前阶段目标和基本运行方式。

### `requirements.txt`

记录当前阶段需要的 Python 依赖。第一阶段二维检测 Demo 计划使用 YOLO 模型，因此主要依赖 `ultralytics`、`opencv-python`、`PyYAML`。

### `environment.stage01.yml`

记录第一阶段可复现的 conda 环境配置。如果现有 `py39` 环境不可用，可以用该文件重新创建独立环境。

当前已检查本机环境，`py39` 环境已安装第一阶段需要的主要依赖，可优先使用 `py39`。

### `configs/stage01_2d_detection.yaml`

二维目标检测 Demo 的配置文件，用于统一管理：

1. 输入图片路径；
2. 输出结果路径；
3. Ultralytics 运行缓存路径；
4. 模型权重路径；
5. 置信度阈值；
6. 设备选择。

后续如果更换模型或数据路径，优先修改配置文件，不直接改代码。

### `code/.cache/ultralytics/`

Ultralytics 默认会读写用户目录下的配置文件。为了让实验尽量留在项目内部，当前配置将 Ultralytics 的配置目录放在这里。

### `data/stage01_2d_detection/input_images/`

存放二维检测 Demo 的输入图片。

建议先放少量道路场景图片，例如 KITTI、nuScenes 前视图像或自己准备的车辆道路图片。

### `models/`

存放本项目实验会用到的模型权重。

当前包含 `yolov8n.pt`，用于阶段 1 的二维目标检测 Demo。后续如果增加三维检测或多模态检测模型权重，也统一放在该目录或其子目录下。

### `models/openpcdet/`

存放服务器复现 PointPillars 时使用的 OpenPCDet 模型权重。默认预期文件名为 `pointpillar_kitti.pth`。

### `models/mmdetection3d/`

阶段 3 多模态三维目标检测模型权重目录。当前用于保存 MVX-Net KITTI 预训练权重。

### `outputs/stage01_2d_detection/`

存放二维检测 Demo 的输出结果，包括：

1. 带检测框的可视化图片；
2. 检测结果 JSON 文件；
3. 后续可能增加的日志文件。

### `outputs/server_pointpillars_demo/`

存放服务器端 PointPillars 单模态三维目标检测展示结果。当前包含：

1. 9 张 `*_pred_bev.png` BEV 检测可视化图；
2. `predictions.json` 结构化检测结果；
3. `inference.log` 推理日志。

该目录只保存模型检测输出，不混放原始点云输入图。它是当前阶段向导师展示“单模态三维目标检测基础系统已跑通”的主要结果目录。

### `outputs/stage02_mono3d_detection/demo_input_bev/`

存放 demo 点云的原始输入 BEV 图。该目录只用于说明 PointPillars 输入点云是什么样子，不包含模型检测框。

### `outputs/stage03_mvxnet_demo/`

存放服务器端 MVX-Net 图像+雷达多模态三维目标检测展示结果。当前包含：

1. `vis_camera/CAM2/000008.png` 相机视角检测展示图；
2. `preds/000008.json` 结构化三维检测结果；
3. `inference.log` 推理日志；
4. `结果展示说明.md` 展示材料说明。

该目录是当前阶段向导师展示“图像+雷达多模态三维目标检测基础系统已跑通”的主要结果目录。

### `src/stage01_2d_detection/run_yolo_demo.py`

第一阶段的核心脚本，负责：

1. 读取配置文件；
2. 加载 YOLO 模型；
3. 读取输入图片或图片文件夹；
4. 执行二维目标检测；
5. 保存带检测框的可视化结果；
6. 保存结构化 JSON 检测结果。

该脚本只做二维检测 Demo，不包含三维检测、多模态融合或退化实验代码，避免结构混乱。

### `src/stage01_2d_detection/summarize_results.py`

阶段 1 的结果汇总脚本，负责读取二维检测输出的 JSON 结果，并生成 Markdown 汇总表。它用于把检测数量、类别统计和按图片统计整理成便于写入开题材料的文本。

## 阶段组织原则

每个阶段只放该阶段相关代码，并在本说明文件中同步解释新增结构。按照导师意见，复杂工况实验应建立在阶段 2 单模态三维检测和阶段 3 图像+雷达多模态三维检测基础系统均跑通的基础上。

## 阶段 2：单模态三维目标检测准备

### `src/stage02_mono3d_detection/check_3d_detection_env.py`

三维检测环境检查脚本，用于记录 Python、PyTorch/CUDA、nvidia-smi 和关键依赖包状态，判断当前机器是否具备复现 PointPillars/CenterPoint 的基础条件。

### `configs/stage02_mono3d_kitti.yaml`

阶段 2 的配置文件，用于管理 KITTI 数据根目录、输出目录和 BEV 可视化范围。

### `data/stage02_mono3d_detection/kitti/`

预留 KITTI object detection 数据目录。后续应将 `training/velodyne`、`training/image_2`、`training/calib`、`training/label_2` 等数据放在这里。

### `data/stage02_mono3d_detection/KITTI数据准备清单.md`

阶段 2 的真实 KITTI 数据准备说明，记录需要下载的压缩包、放置位置、自动整理命令、数据检查命令和 BEV 可视化命令。

### `data/stage02_mono3d_detection/demo_samples/`

服务器检测展示版点云目录，默认放置 KITTI 格式 demo 点云。当前包含基础点云 `000008.bin` 和 8 个展示用变体，共 9 个 `.bin` 点云文件。变体只用于生成更多检测展示图，不作为正式实验数据。

### `src/stage02_mono3d_detection/check_kitti_dataset.py`

KITTI 数据检查脚本，用于确认点云、图像、标定和标签文件是否齐全，并生成 Markdown 检查报告。

### `src/stage02_mono3d_detection/check_kitti_archives.py`

KITTI 压缩包检查脚本，用于确认下载目录中是否已经放入 `velodyne`、`calib`、`label_2`、`image_2` 四个压缩包，并生成 Markdown 状态报告。

### `src/stage02_mono3d_detection/prepare_kitti_archives.py`

KITTI 压缩包整理脚本，用于把已下载的 KITTI object detection 压缩包解压到阶段 2 约定的数据目录。

### `src/stage02_mono3d_detection/create_synthetic_kitti_sample.py`

合成 KITTI 风格样例生成脚本，仅用于验证点云读取和 BEV 可视化链路，不作为论文实验数据。

### `src/stage02_mono3d_detection/visualize_demo_inputs_bev.py`

PointPillars demo 点云输入可视化脚本，用于把 `data/stage02_mono3d_detection/demo_samples/` 中的 `.bin` 点云生成无检测框的 BEV 输入图。默认输出到 `outputs/stage02_mono3d_detection/demo_input_bev/`，避免和检测结果混放。

### `src/stage02_mono3d_detection/visualize_kitti_bev.py`

KITTI 点云 BEV 可视化脚本，用于读取 velodyne 点云文件并生成俯视图。该脚本是进入 PointPillars/CenterPoint 前的数据链路检查工具。

### `src/stage02_mono3d_detection/visualize_kitti_bev_with_labels.py`

KITTI 点云和三维标签框 BEV 可视化脚本。真实 KITTI 数据使用标定文件将相机坐标标签转换到雷达坐标后绘制；合成样例使用雷达坐标标签，仅用于程序自测。

## 阶段 4：复杂工况样例与检测对比

### `configs/stage04_complex_conditions.yaml`

阶段 4 配置文件，定义复杂工况类型和一对一生成规则。当前工况包括弱光、雾天、运动模糊、图像噪声、点云稀疏、点云扰动和图像+点云联合退化。

其中，运动模糊和图像噪声主要用于模拟相机图像退化，点云稀疏和点云扰动主要用于模拟激光雷达数据退化。这些工况可用于分析多模态三维检测在复杂环境下的稳定性变化。

### `data/stage04_complex_conditions/base_samples/`

复杂工况实验的干净原始样例目录。每个原始样例必须包含 `.png`、`.bin`、`.pkl` 三件套。

### `data/stage04_complex_conditions/condition_samples/`

复杂工况样例输出目录。生成脚本会保证每个原始样例最多只对应一种复杂工况，不采用一帧扩展多种工况的方式。

### `data/stage04_complex_conditions/paired_samples/`

复杂工况成组对比目录。每个对比组包含 `clean/` 和 `complex/` 两个子目录，分别保存改变前原始数据和改变后复杂工况数据。服务器批量检测优先读取该目录。

### `src/stage04_complex_conditions/create_one_to_one_conditions.py`

阶段 4 复杂工况样例生成脚本。它按配置顺序扫描多个原始样例，并为每个样例分配一种复杂工况，生成新的图像、点云和元数据三件套，同时整理出 `clean/complex` 成组对比结构。

### `src/stage04_complex_conditions/make_detection_comparison_previews.py`

阶段 4 检测结果对比图生成脚本。服务器结果复制回本地后，可读取 `mvxnet_comparison_results/` 中的 `clean` 和 `complex` 检测图，生成并排对比图。

### `outputs/stage04_complex_conditions/`

阶段 4 报告、预览和检测对比输出目录。当前包含复杂工况样例生成报告、改变前/改变后输入预览、服务器 MVX-Net 检测结果，以及整理后的检测对比图。

重点查看：

```text
outputs/stage04_complex_conditions/detection_comparisons/
outputs/stage04_complex_conditions/detection_comparisons/summary.md
outputs/stage04_complex_conditions/复杂工况展示说明.md
```

当前验收结论是：弱光和雾天对该批样例影响相对较轻；运动模糊、图像噪声、点云稀疏和点云扰动更能体现复杂工况下的检测可靠性下降，表现为高置信目标减少、少量漏检或平均置信度下降。展示和报告中应避免夸大为“所有复杂工况都导致检测失败”。
